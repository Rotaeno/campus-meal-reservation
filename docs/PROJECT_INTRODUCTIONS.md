# 校园午餐项目简历与面试介绍

项目名称建议使用“校园午餐预订与自提系统”。项目定位是基于苍穹外卖教学项目完成的个人改造，重点是业务规则、订单正确性与故障恢复。下面三份介绍对应简历、面试开场和项目追问，使用的并发数字来自本地实际检查。

## 简历介绍

**校园午餐预订与自提系统｜基于苍穹外卖的个人改造**

**技术栈：** Java、Spring Boot、MyBatis、MySQL、Redis、Vue、JWT、WebSocket、Flyway。

**项目描述：** 面向校园午餐集中备餐与分时取餐，提供餐次发布、限额预订、订单处理、备餐统计、自提核销和取消退款功能，配套用户预订页及商家管理页。

- **项目概述**：基于Spring Boot、MyBatis、MySQL改造苍穹外卖，新增校园餐次发布、限额预订与取餐核销，重点处理重复下单、容量竞争和异常退款。
- **下单一致性**：以用户与请求键唯一约束持久化幂等，用户行锁协调购物车与结算；服务端计价并保存快照，通过条件SQL预占份数，将容量、订单明细及清购物车纳入同一事务。
- **状态与退款**：通过条件更新控制状态迁移；以持久化任务、稳定退款号及租约支持退款恢复，分离扫描与外部调用，采用有界工作池隔离慢退款对调度的影响。
- **并发与故障验证**：本地双实例与独立持久化模拟账本下验证同键下单、容量竞争和进程中断恢复；基于独立状态模型检查同单并发操作及已提交变化，区分自动恢复与回调重投。

典型数量结果为50个同键请求仅1单、20用户争5份成功5单、20次并发核销仅1次，可根据版面在第四条保留一组；不要追加未经测量的线上规模或性能提升比例。新模型检查及调度对照的准确范围见[本轮说明](STATE_HISTORY_AND_SCHEDULING.md)。

## 面试开场短介绍

我做过一个校园午餐预订与自提项目，是在苍穹外卖基础上完成的个人改造。学生按餐次提前预订，商家按份数集中备餐，再凭取餐码核销。我重点改造了订单链路，包括服务端计价、持久化下单幂等、餐次名额控制、状态迁移和退款重试。验证时，同一请求的50次并发提交只生成一单，20个用户争抢5份名额也没有超卖。这个项目让我对事务边界、并发冲突和外部调用失败后的恢复有了比较具体的理解。

## 项目展开长介绍

我这个项目叫校园午餐预订与自提系统，是基于苍穹外卖教学项目做的个人改造。原项目已经有菜品、套餐、购物车、订单和管理端，我保留了这些基础能力，增加了校园午餐预约场景。这个场景的特点是商家按餐次集中备餐，每个餐次有可售份数和截单时间，学生需要在指定时间段取餐。因此我主要围绕“预约名额能否正确扣减、订单会不会重复、异常支付和退款如何恢复”改造订单链路。

业务上，商家先发布餐次，设置容量、截单时间和自提时段。学生选择餐次和菜品，服务端计算价格并创建订单，同时预占所选餐品的份数。支付后，商家接单并查看按菜品汇总的备餐数量；备餐完成后标记为待自提，工作人员在取餐时段内用取餐码核销。未支付订单超过15分钟或者餐次已经截单，会被定时任务取消。截单前且尚未接单的订单允许学生取消；接单后或者截单后的异常情况由商家处理。

第一个改造是服务端计价。原来的订单提交链路会使用客户端提交的金额，这样客户端改参数就可能影响订单总价。我现在重新读取数据库中的菜品或套餐价格与销售状态，用BigDecimal计算总额，餐盒费按份收取，自提不收配送费，再保存订单明细的名称、价格和数量快照。客户端金额以及购物车里被篡改的单价都不能决定最终结算金额。菜单之后改价，也不会改变已生成订单的价格。

第二个改造是持久化下单幂等和容量控制。用户开始一笔预订时生成请求键，网络失败时保留原请求重试。服务端以用户ID和请求键建立唯一约束，并保存请求内容的指纹。同一个键再次提交会返回已有订单，修改备注或取餐信息后继续复用这个键则会被拒绝。购物车修改和结算都先锁定当前用户行，协调同一用户的并发操作；餐次份数通过带容量条件的SQL原子增加。容量、订单主表、明细和购物车清理都在一个事务中，所以任何一步失败都会整体回滚。

这里我还在实际并发测试中遇到过锁冲突。购物车表最初缺少按用户查询的索引，加上锁定查询后会扫描并锁定过多记录。我补充了用户范围索引，同时把下单和报价事务设为READ COMMITTED，以减少不存在的请求键查询带来的间隙锁干扰。正确性仍然依靠用户行锁、菜单共享锁、唯一约束和餐次条件更新来保证。这个过程让我认识到，加事务或者加锁之后还需要分析SQL真正扫描的记录范围。

第三个改造是订单状态和退款恢复。接单、备餐就绪、核销都使用带原状态和已支付条件的更新，并检查影响行数，避免重复操作和越过流程。自提订单不能走普通配送完成接口，只能在有效时间段内凭随机码核销。支付与取消都锁定订单行；重复支付通知不会重复推进状态，超时或取消之后收到支付成功通知，也不会恢复原订单，而是保持取消并创建退款任务。

退款方面，我把“取消成功”和“退款成功”分开表达。取消时，在同一数据库事务中写入退款任务，然后由后台任务在事务外调用支付平台。每次重试复用同一个退款号，通过租约领取和条件更新协调任务执行，网络失败后退避重试，累计失败达到阈值进入可见的失败状态并支持商家人工重试。只有支付平台确认成功后，订单才显示已退款。如果服务在调用过程中退出，过期租约可以重新领取；这解决的是可恢复的最终一致性，真实资金状态还需要查单和对账来确认。

验证方面，历史检查中50个同键请求只产生一个订单，20用户争抢5份只成功5单，20次核销只成功一次。后续使用双实例、独立持久化模拟账本及实际进程中断，检查提交前回滚、提交后原键重放和退款恢复；持续负载还定位过取消操作的外键锁升级死锁，以及慢退款占用调度线程的问题，分别调整锁顺序和任务执行方式。

为了检查过程，我又用独立业务模型验证同一订单并发操作的响应和实时先后关系，并在隔离测试库记录随事务提交或回滚的状态变化；同步阶段不靠最后补发支付、取消来收敛，退款自动恢复另行检查。同一构建包还做了三轮调度对照，分清增加调度线程和分离外部调用各自解决的问题。支付回调在外部记账后丢失时，当前仍需要回调重投；没有主动支付对账。支付资金全模拟，跨机器、数小时运行及历史建连超时归因仍未完成。

## 常见追问

**最终数据对了，为什么还检查操作历史？**

最终状态可能掩盖非法中间变化，也可能依赖测试脚本最后补发的请求。本轮把完整HTTP操作交给独立模型，检查是否存在符合业务规则和实时先后关系的顺序；隔离库事务内记录再检查提交链，异步退款与显式回调重投分开。24组/126次操作通过只代表这些有限历史，不是全局正确性证明。详见[状态历史说明](STATE_HISTORY_AND_SCHEDULING.md)。

**退款在事务外，为什么还需要独立工作池？**

事务外降低数据库锁持有时间，原逐笔调用仍占用共用调度线程。先用5秒延迟复现，再分离扫描和执行，默认2个退款线程、16个排队位置，实际执行时领取租约。本轮18组对照说明：只增加调度线程可隔离超时扫描，普通退款仍逐笔等待；异步且有空闲工作线程时可并行，工作线程全满仍需排队。对应[后台恢复记录](BACKGROUND_RECOVERY.md)与[调度对照](STATE_HISTORY_AND_SCHEDULING.md)。

**为什么没有直接上Redis分布式锁和消息队列？**

容量、购物车和订单都存储在同一个MySQL中，数据库行锁与条件更新能和事务一起提交或回滚，适合当前规模。进程内锁无法协调多实例；Redis锁还需要处理锁失效与数据库提交之间的关系。退款使用可持久化任务表先满足恢复需求，规模增加后可以引入消息队列，但仍要保留业务幂等和数据库状态判断。

**唯一索引已经存在，为什么还锁用户行？**

唯一索引防止同一个键重复写入，用户行锁还协调同一用户使用不同请求键同时结算，以及购物车加减与结算的竞争。没有这层协调，两个结算事务可能读取同一份购物车。它不是所有用户共用的一把锁，不同用户仍能独立执行，只有争抢同一餐次容量时才竞争餐次行。

**请求指纹为什么不包含购物车？**

第一次成功后购物车会被清空，重试时不能根据当前购物车重新判断原请求。当前协议把一个请求键定义为一次购物车结算，指纹校验餐次、联系信息、备注等提交参数。重试永远返回这次结算的历史结果；开始另一笔必须生成新键。若未来要支持多设备编辑中的严格版本语义，可以增加购物车版本或持久化结算草稿。

**退款接口超时，但平台实际上已经退款怎么办？**

单次超时不等于平台退款失败，也不能因此生成新退款号。当前复用稳定退款号，返回处理中后改用查询；累计六次本地失败转FAILED待人工处理，这不证明资金未退。长期结果未知、退款通知和主动对账仍需完善。

**能保证完全不死锁吗？**

不能。当前通过索引、锁顺序和局部READ COMMITTED降低锁冲突，并对明确MySQL死锁/锁超时最多尝试3次，每次完整回滚后开启新事务。持续负载曾发现取消中的外键S到X锁升级，已调整为同事务中先释放容量，再改订单状态；有实测及失败回滚证据。这仍不意味着所有竞争组合都不会死锁。

**能保证WebSocket消息不丢吗？**

当前在数据库提交后发送，避免事务回滚却通知商家；通知尚未持久化，也没有断线补偿。商家可通过数据库订单列表刷新恢复视图。更严格的可靠通知应增加outbox和消费确认，不能把当前实现称为消息恰好投递一次。

**项目有哪些真实接入和验证边界？**

业务数据库、缓存、HTTP和Vue构建是真实运行；微信授权、支付、退款、云存储和地图使用local适配。非local支付协议有RSA与AES-GCM样本测试，但还需要真实商户凭证、证书管理、回调部署和对账联调。当前也未完成浏览器自动点击和微信开发者工具验收。
