## 相较原始苍穹外卖改了什么

对照基准是README标明的上游提交，不代表所有同名课程版本。菜品、套餐、员工、登录、基础购物车、报表及Redis菜单缓存主要沿用上游，个人改造重点如下。

| 改进方向 | 原始苍穹外卖基线 | 本项目的改进与作用 |
| --- | --- | --- |
| 校园业务（新增） | 主要是即时外卖，没有校园餐次限额与自提核销 | 发布餐次、设置份数和截单时间，集中备餐、到点凭码取餐 |
| 金额计算（修复） | 下单链路会复制客户端提交的金额 | 后端按数据库菜单重算，保存名称、单价和数量快照，防参数改价 |
| 订单事务与容量（修复＋新增） | 订单、明细和清购物车未统一事务；没有餐次容量 | 将预占份数、写单和清购物车一起提交或回滚，条件SQL防超卖 |
| 重复下单（新增协议） | 缺少持久化的请求级幂等与购物车结算协调 | 用户＋请求键唯一；同键同参数返回原单，用户锁协调不同键结算与加购 |
| 状态与迟到支付（修复＋新增） | 部分状态操作存在竞争或实现错误 | 按原状态条件更新；取消只释放一次，取消后收到支付也不恢复订单，而是退款 |
| 异常退款（重构） | 同步调用退款，缺少持久化任务及中断恢复链路 | 先存任务、事务外调用、原号查询、租约恢复；区分本地失败和平台结果，人工恢复留记录 |
| 并发排障（迭代自身方案） | 不直接归为原始项目的缺陷 | 在改造中复现外键锁升级、慢退款阻塞调度和整批候选受锁；调整锁顺序、有界工作池及跳锁扫描 |
| 权限、查询及验证（补齐） | 部分对象操作缺少归属校验，分页逐单查明细；缺少本项目场景的验证证据 | 补用户归属和身份清理、批量查明细；增加双实例、真实进程中断、独立账本与状态历史检查 |

先掌握四件事：业务怎样走、请求为何不会多建单、名额和订单怎样一起回滚、外部退款怎样恢复。死锁、有界线程池、SKIP LOCKED和状态历史模型再作为深入追问；这些是已有链路的深化。

## 面试开场介绍（约一至两分钟）

这个项目是我基于苍穹外卖做的校园午餐预订与自提系统。菜品、登录等基础模块沿用原项目，我主要新增餐次限额和取餐核销，并改造订单链路，后端使用Spring Boot、MyBatis和MySQL。

我主要处理三个问题。第一是重复下单，通过用户与请求键唯一约束保存结果，同键同参数重试返回原订单，并用用户行锁协调购物车和结算。第二是名额竞争，通过条件SQL预占份数，把名额、订单明细和清购物车放在一个事务中，失败一起回滚。第三是退款恢复，取消已支付订单时先保存退款任务，外部调用放在事务外，后续尝试先查原退款号，再通过租约和重试处理进程中断，确认成功后才更新已退款状态。

我用本地双实例、独立模拟账本和进程中断验证这些路径，也排查过并发取消中的外键锁升级死锁。支付和退款资金目前仍是模拟，没有真实商户对账。

## 项目展开说明

业务上，商家先设置餐次容量、截单时间和取餐时段；学生选择菜品，下单预占份数，支付后商家接单、按菜品汇总备餐，最后在指定时段凭随机码核销。基础管理模块来自上游，我新增校园规则、页面与订单可靠性改造。

下单时，服务端先锁当前用户行，查是否已有同一请求键的订单。存在且指纹相同就返回原订单，不同则拒绝复用；购物车已经清空或服务重启，也不影响历史结果。首次没有提交结果时，按当时购物车和数据库菜单重新计价，保存价格快照。用户行锁还协调不同键结算与购物车加减，唯一约束则防同键重复写入，两者职责不同。

容量判断和增加放在同一条条件UPDATE中，影响一行才允许继续。容量、订单主表、明细和购物车清理处于同一个事务。状态迁移检查原状态及支付条件；取消只释放一次，核销不再释放已售份数。取消后收到迟到支付，保持取消并创建退款任务。

退款分成“保存意图、领取任务、外部调用、确认结果”。取消与退款意图在同一事务，网络调用在事务外，重试始终沿用稳定退款号。后续尝试先查原号，明确未找到才同号同金额重提；租约支持进程退出后换人执行，领取令牌阻止旧执行者覆盖本地结果。六次本地失败或长期处理中会转人工，但这不等于平台未退款。人工重置、原因和操作人记录一起提交。

一个具体案例是：模拟端已实际退款，第一次响应异常，之后五次查询也失败。本地停止自动处理时记录“结果未知”，订单不提前显示已退款；人工恢复并重启服务后，查询原号完成确认。独立账本最终是一次退款POST、六次查询、一次实际退款。它说明本地确认可以恢复，不能据此保证外部接口恰好调用一次。

并发测试还定位过取消先改子订单状态、再释放父餐次容量引起的S锁到X锁升级死锁，改为同一事务内先释放容量再改状态。后来分离退款扫描和网络执行，避免慢调用占调度线程；候选用短事务跳过已锁行，实际执行再领取租约。这些都有复现和修复后的检查，并不表示所有竞争都不会死锁。

验证包括历史小批并发结果、双实例竞争、真实中断自有进程、独立模拟账本，以及24组同单历史的126次操作。当前构建63项Java单测通过，最新退款核查14项通过；十万任务用于查询计划与扫描检查，不是十万真实用户。支付资金全模拟，没有主动支付对账、跨机器和数小时稳定性验收。

## 常见追问

**最终数据对了，为什么还检查操作历史？**

最终状态可能掩盖非法中间变化，也可能依赖测试脚本最后补发的请求。本轮把完整HTTP操作交给独立模型，检查是否存在符合业务规则和实时先后关系的顺序；隔离库事务内记录再检查提交链，异步退款与显式回调重投分开。24组/126次操作通过只代表这些有限历史，不是全局正确性证明。详见[状态历史说明](STATE_HISTORY_AND_SCHEDULING.md)。

**退款在事务外，为什么还需要独立工作池？**

事务外降低数据库锁持有时间，原逐笔调用仍占用共用调度线程。先用5秒延迟复现，再分离扫描和执行，默认2个退款线程、16个排队位置，实际执行时领取租约。本轮18组对照说明：只增加调度线程可隔离超时扫描，普通退款仍逐笔等待；异步且有空闲工作线程时可并行，工作线程全满仍需排队。对应[后台恢复记录](BACKGROUND_RECOVERY.md)与[调度对照](STATE_HISTORY_AND_SCHEDULING.md)。

**为什么没有直接上Redis分布式锁和消息队列？**

容量、购物车和订单都存储在同一个MySQL中，数据库行锁与条件更新能和事务一起提交或回滚，适合当前规模。进程内锁无法协调多实例；Redis锁还需要处理锁失效与数据库提交之间的关系。退款使用可持久化任务表先满足恢复需求，规模增加后可以引入消息队列，但仍要保留业务幂等和数据库状态判断。

**唯一索引已经存在，为什么还锁用户行？**

唯一索引防止同一个键重复写入，用户行锁还协调同一用户使用不同请求键同时结算，以及购物车加减与结算的竞争。没有这层协调，两个结算事务可能读取同一份购物车。它不是所有用户共用的一把锁，不同用户仍能独立执行，只有争抢同一餐次容量时才竞争餐次行。

**请求指纹为什么不包含购物车？**

第一次成功后购物车会被清空，重试时不能根据当前购物车重新判断原请求。当前协议把一个请求键定义为一次购物车结算，指纹校验餐次、联系信息、备注等提交参数。已有提交结果时返回历史订单；若首次从未提交，重试按当时购物车和服务端价格结算。开始另一笔必须生成新键。若未来要支持多设备编辑中的严格版本语义，可以增加购物车版本或持久化结算草稿。

**退款接口超时，但平台实际上已经退款怎么办？**

单次超时不等于平台退款失败，也不能因此生成新退款号。后续尝试先查询原号，明确NOT_FOUND才同号同金额重提；六次本地失败转FAILED待人工，providerState另存最后平台结果。人工恢复须原因并记录操作人，重置与记录同事务，仍先查原号。平台关闭/异常仍需平台侧处置，退款通知及主动对账尚未完成。[实现与证据](REFUND_REVIEW.md)

**能保证完全不死锁吗？**

不能。当前通过索引、锁顺序和局部READ COMMITTED降低锁冲突，并对明确MySQL死锁/锁超时最多尝试3次，每次完整回滚后开启新事务。持续负载曾发现取消中的外键S到X锁升级，已调整为同事务中先释放容量，再改订单状态；有实测及失败回滚证据。这仍不意味着所有竞争组合都不会死锁。

**能保证WebSocket消息不丢吗？**

当前在数据库提交后发送，避免事务回滚却通知商家；通知尚未持久化，也没有断线补偿。商家可通过数据库订单列表刷新恢复视图。更严格的可靠通知应增加outbox和消费确认，不能把当前实现称为消息恰好投递一次。

**项目有哪些真实接入和验证边界？**

业务数据库、缓存、HTTP和Vue构建是真实运行；微信授权、支付、退款、云存储和地图使用local适配。非local支付协议有RSA与AES-GCM样本测试，但还需要真实商户凭证、证书管理、回调部署和对账联调。当前也未完成浏览器自动点击和微信开发者工具验收。
